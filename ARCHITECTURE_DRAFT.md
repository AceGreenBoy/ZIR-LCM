# Архитектура сервера прошивок для ESP32 (черновик)

Это черновой каркас. Детали зависят от ответов на вопросы ниже. К каждому вопросу записан вариант, который выбирается по умолчанию.

## Черновой каркас

```
                 ┌──────────────────────── Go backend ────────────────────────┐
 Инженер ──HTTPS+2FA──► API Gateway ──► Auth/RBAC (инженеры, роли, лицензии)  │
 (Web/CLI)        │         │      ──► Device Registry (устройства, HW-конфиг) │
                  │         │      ──► License/Revocation (блокировки, CRL)    │
 ESP32 ──mTLS────►│         │      ──► Firmware Catalog / Builder              │
 (OTA)            │         │      ──► Signing Service ──► HSM / Vault / KMS   │
                  │         └────► Audit Log (append-only)                     │
                  └──── PostgreSQL ── S3/MinIO (артефакты) ────────────────────┘

 Provisioning Tool (Go CLI у производителя) ──USB──► ESP32 при первой прошивке
```

### Роли

- `manufacturer` регистрирует новые устройства.
- `engineer` входит в инженерное меню.
- `admin` управляет лицензиями и отзывом.

### Основные сценарии

1. **Первая прошивка.** Производитель логинится в CLI. Устройство генерирует ключевую пару, и сервер выпускает на неё сертификат от Device CA. Затем включаются Secure Boot v2 и Flash Encryption, и устройство записывается в БД вместе с HW-конфигом и ID производителя.
2. **OTA.** Устройство приходит на сервер с mTLS-сертификатом. Сервер проверяет, что устройство не заблокировано и сертификат не отозван. Потом подбирает образ под HW-конфиг и отдаёт подписанный бинарник.
3. **Инженерное меню.** Инженер получает на сервере короткоживущий токен. Токен подписан сервером и привязан к паре `engineer_id + device_id`. Устройство проверяет подпись встроенным публичным ключом.
4. **Отзыв.** Устройство или инженер помечаются отозванными. Сертификат устройства уходит в CRL, его OTA блокируется. Новые токены инженеру больше не выдаются.

## Уточняющие вопросы

### Железо и шифрование

1. **Какой чип: ESP32 classic, S3, C3 или C6?** Это критично. У S3, C3 и C6 есть периферия Digital Signature: приватный ключ устройства хранится в eFuse и не извлекается. На classic ESP32 её нет, и клонирование сложнее предотвратить.
   *По умолчанию: S3 или C6.*
Обычный ESP32 WROOM на 4МБ

2. **Где генерировать ключ Flash Encryption?** Вариант первый: на самом устройстве, и он никому не известен. Вариант второй: на сервере, с хранением ключа для каждого устройства. Второй вариант нужен, только если сервер должен отдавать заранее зашифрованный образ для прошивки по USB.
   *По умолчанию: на устройстве, в Release mode.*
Давай так чтоб был на сервере, и я хочу чтоб пока не было прожига eFuse. Чтоб вся система работала, а прожиг был опциональным. Нужно чтоб прошивка не запустилась на другом устройстве но само устройство можно было бы прошить другой прошивкой. Пока это решение не принято бизнесом.

3. **Что значит «конфигурация железа»?** Это несколько ревизий плат или модулей (готовые варианты сборки)? Или комбинации периферии, под которые нужна сборка на лету?
   *По умолчанию: заранее собранные варианты плюс персональный NVS-раздел с конфигом для каждого устройства. Сборка ESP-IDF на лету в Docker медленная и усложняет воспроизводимость.*
Есть несколько вариантов комбинаций модулей и их диапазонов работы которые зависят от железа. Возможно получится обойтись просто набором готовых вариантов. Но тогда получится ли собирать прошивку которую запускается только на конкретном устройстве и если ее установить на другое то она не запустится.

4. **Кто определяет конфиг?** Устройство само сообщает, что на нём стоит? Инженер вводит при регистрации? Или конфиг берётся из БД по SKU или серийнику?

## Раунд 2: выводы из ответов

### Главное ограничение: ESP32 classic без прожига eFuse

Без Secure Boot и Flash Encryption любой человек с USB-UART может считать flash командой `esptool.py read_flash`. Всё, что лежит на устройстве, читается открытым текстом: прошивка, ключи, сертификат. Поэтому:

- **Программную привязку прошивки к устройству можно обойти.** Проверку «я запущен на своём MAC» злоумышленник найдёт в дампе и пропатчит. Это защита от случайного копирования, но не от целенаправленного клонирования.
- **Ключ устройства для mTLS можно скопировать.** Клон с этим ключом сможет представиться оригиналом. Частично это ловится на сервере: два «одинаковых» устройства с разных IP, несовпадение заявленного MAC.
- **Настоящую защиту даёт только eFuse.** Систему стоит строить так, чтобы прожиг включался позже без переделки сервера.

### Предлагаемый подход: уровни защиты

| Уровень | Что включено | От чего защищает |
|---|---|---|
| **L0** (сейчас) | Pre-encrypted OTA с персональным ключом устройства, подписанный сервером конфиг, проверка MAC, mTLS, проверки на сервере | Незарегистрированное устройство не получит прошивку. Перехваченный OTA-образ бесполезен для другого устройства. Нельзя войти в инженерный режим без сервера. |
| **L1** (по решению бизнеса) | L0, плюс Flash Encryption с ключом, сгенерированным на сервере. Режим Development, перепрошивка по UART разрешена. | Дамп flash не даёт ни прошивки, ни ключей. Образ, зашифрованный под одно устройство, не запустится на другом. |
| **L2** (опционально) | L1, плюс Secure Boot V2 и режим Release | Запускается только прошивка, подписанная вашим ключом. Устройство нельзя перепрошить чужой прошивкой. |

Это отвечает на вопрос 3, «прошивка под конкретное устройство»: компилировать отдельный бинарник под каждое устройство не нужно.

1. Сервер хранит несколько **вариантов сборки**, по одному на комбинацию модулей.
2. Для конкретного устройства сервер берёт подходящий вариант и **шифрует его персональным ключом устройства**. Для этого есть компонент ESP-IDF `esp_encrypted_img` (pre-encrypted OTA). Получается уникальный образ: на другом устройстве его нечем расшифровать.
3. Рабочие диапазоны модулей лежат в **конфиге, подписанном сервером**. Конфиг содержит `device_id` и MAC устройства. Прошивка не стартует, если подпись неверна или MAC не совпадает.

На уровне L0 персональный ключ устройства лежит в flash открытым текстом. Шаг 2 защищает при передаче и от простого копирования образа, но не от того, кто считал flash оригинального устройства. На уровне L1 этот пробел закрывается.

### Нестыковки, которые нужно прояснить

- **«Только OTA»** не работает для первой прошивки: на чистое устройство что-то нужно один раз записать по USB. Предложение: производитель через Provisioning Tool прошивает по USB минимальную **bootstrap-прошивку**. Она только регистрируется на сервере и скачивает рабочую прошивку по OTA. Рабочая прошивка по USB не распространяется.
- **Wi-Fi и обращение к серверу.** Инженер подключается к устройству по Wi-Fi. Если это точка доступа самого устройства, интернета нет ни у устройства, ни у телефона инженера (телефоны часто не пускают трафик через мобильную сеть, когда Wi-Fi без интернета). Тогда проверить инженера на сервере невозможно. Нужно понять реальную схему подключения (вопрос R2-3).

bootstrap прошивка по USB и дальше рабочая через сервер это то что нужно. Пока у меня план что подключаешься к устройству, вводишь пароль для вайфай с интернетом и дальше работаешь с устройством и с доступом в интернет.
### Предложение по инфраструктуре (VPS)

Для 10 человек и сотен устройств хватит одной VPS: 2 vCPU, 4 ГБ RAM, 40+ ГБ диска.

- **Docker Compose**: Go-сервер, PostgreSQL и Caddy (обратный прокси с автоматическим HTTPS от Let's Encrypt).
- **Артефакты прошивок** хранятся на диске VPS. MinIO не нужен на таком масштабе.
- **Секреты.** Без HSM используется envelope encryption: ключи устройств шифруются мастер-ключом, мастер-ключ лежит вне БД (файл или переменная окружения). Vault на таком масштабе избыточен.
- **Ключ подписи прошивок** (на будущее, для Secure Boot) хранится **не на VPS**, а на машине сборки или в CI. Если VPS взломают, подписать чужую прошивку не получится.
- **Резервные копии** PostgreSQL и мастер-ключа делаются ежедневно в отдельное хранилище. Потеря ключей устройств на уровне L1 означает, что OTA-образы под эти устройства больше не собрать.
- Веб-админка: SPA или серверные шаблоны на Go. Вход по логину и TOTP.

## Раунд 3: что зафиксировано

- **Чип:** ESP32 classic WROOM, 4 МБ. Прошивка на ESP-IDF 6.0.3. Разметка: два OTA-слота по 1,5 МБ.
- **Защита:** уровень L0, eFuse не прожигаются. Сервер и прошивка проектируются так, чтобы позже можно было включить L1 без переделки.
- **Первая прошивка:** производитель записывает bootstrap-прошивку по USB. Затем через веб-морду устройства вводит пароль Wi-Fi, устройство регистрируется в БД и получает рабочую прошивку по OTA.
- **Связь:** основной вариант — устройство подключено к Wi-Fi с интернетом (вариант «а»). Вариант «б» поддерживается тем же протоколом, см. ниже.
- **Пользователи:** управляют устройством локально без интернета. При подключении к интернету могут проверить обновления и обновиться, если устройство не отозвано.
- **Прошивки:** отдельная сборка под каждую конфигурацию железа. Сборка идёт на сервере из веток git. Каналы `beta` и `stable`; автоматически устанавливается только `stable`.
- **Откат версии:** только инженер.
- **Роли:** `superadmin` (один человек), `admin` (только просмотр статистики и данных устройств), `manufacturer`, `engineer`. Одному человеку можно выдать несколько ролей.
- **Хостинг:** VPS с доменом. Reverse proxy и сертификаты Let's Encrypt уже настроены, поэтому Caddy из предложения убирается.

### Как работает вход инженера в обоих вариантах связи

1. Инженер открывает веб-морду устройства и нажимает «Инженерный вход».
2. Устройство генерирует одноразовый `nonce` и перенаправляет браузер на сервер, передавая `device_id` и `nonce`.
3. Инженер логинится на сервере по логину и TOTP. Сервер проверяет, что инженер и устройство не отозваны.
4. Сервер возвращает браузер на устройство с токеном. Токен подписан сервером, содержит `engineer_id`, `device_id` и `nonce` и живёт 5 минут.
5. Устройство проверяет подпись встроенным публичным ключом сервера, совпадение `nonce` и срок действия. После этого открывается инженерная сессия.

В варианте «а» до сервера ходит браузер инженера, а устройство дополнительно может проверить токен на сервере онлайн. В варианте «б» до сервера ходит только телефон инженера по мобильной сети, а устройство проверяет токен офлайн. Отзыв всё равно срабатывает: отозванному инженеру сервер не выдаст новый токен, а старый проживёт не больше 5 минут.

Риск варианта «б»: некоторые телефоны при подключении к точке доступа без интернета не пускают запросы к серверу через мобильную сеть. Это нужно проверить на реальных телефонах инженеров.

### Важное дополнение к L0: проверка подписи OTA без прожига eFuse

В ESP-IDF есть режим «Signed App Verification Without Hardware Secure Boot» (`CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT`). Устройство принимает по OTA только образ, подписанный вашим ключом, и при этом ни один eFuse не прожигается. Подменить прошивку через OTA тогда нельзя, хотя по USB перепрошить по-прежнему можно. Это ровно то, что нужно сейчас.

Для схемы подписи RSA (как в Secure Boot V2) на ESP32 classic нужна ревизия чипа v3.0 или новее. Поэтому ревизия важна уже для уровня L0, а не только для L2.

### Ответ на R3-3: одна кодовая база и профили сборки

Рекомендация: один репозиторий, модули включаются опциями Kconfig.

- В коде модули оборачиваются в `#ifdef CONFIG_MODULE_X`, то есть ваш вариант с `#ifdef` остаётся.
- Флаги задаются не вручную в коде, а в файле профиля `profiles/<профиль>/sdkconfig.defaults`. Сервер собирает каждый профиль отдельно.

**Как не рассылать обновление устройствам, которых оно не касается:**
1. Каждый билд содержит в описании приложения ID профиля. Сервер отдаёт устройству только билды его профиля из БД. Само устройство тоже проверяет ID профиля в новом образе и отклоняет чужой. Это защищает от «кирпича» из-за ошибки.
2. Релиз — это версия плюс **список профилей, к которым он относится**. Создавая релиз, `superadmin` отмечает профили. Устройства с неотмеченными профилями остаются на текущей версии и обновление не видят.
3. В помощь `superadmin` сервер сравнивает новый бинарник профиля с предыдущим, не учитывая номер версии и дату сборки (включается `CONFIG_APP_REPRODUCIBLE_BUILD`). Если код профиля не менялся, сервер помечает: «для профиля X изменений нет», и галочку можно не ставить.

  - Bootstrap-прошивка тоже подписывается боевым ключом. В этом режиме устройство проверяет новый образ ключом из подписи текущей прошивки, поэтому ключ подписи нельзя потерять, а его смена — отдельная процедура.
- **Репозиторий:** GitHub (приватный). Сервер забирает код по deploy key только для чтения.
- **Пароль:** вида `zir-XXXXX`, постоянный, один и тот же для точки доступа и для веб-морды. Генерируется при первой настройке и отображается на экране устройства. На веб-морде после 5 неудачных попыток вход блокируется на несколько минут.
- **Телеметрия** отправляется при каждом подключении к серверу и защищается двумя слоями поверх HTTPS:
  - **Подпись ключом устройства и монотонный номер пакета.** Сервер отклоняет поддельные и повторно отправленные пакеты.
  - **Шифрование открытым ключом сервера** (X25519 + AES-GCM). Даже при перехвате трафика, в том числе на прокси, содержимое не прочитать.
  - Сервер хранит последнее значение часов наработки и помечает устройство, если счётчик уменьшился.
  - Ограничение L0: человек с USB может изменить счётчик в памяти устройства до отправки. Сервер такое уменьшение обнаружит, но предотвратить его до L1 нельзя.
- **Обновления:** автоматической установки нет. Устройство само проверяет наличие обновлений, а установка происходит по кнопке «Обновить» у пользователя. Версия, которую поставил инженер, сама не меняется.

- **Сборка** запускается только `superadmin`: по кнопке в админке или по webhook в `beta`. Перевод в `stable` идёт без пересборки.
- **Кнопка «Обновить»** предлагает только `stable` новее установленной версии. Откат на `stable` не предлагается.
- **Критические релизы** нужны (детали в R6-4).
- **Core dump** после падения отправляется на сервер вместе с телеметрией, в зашифрованном виде.

### Как устроено обновление `www` (вариант «б»)

Релиз для профиля состоит из двух артефактов: `app.bin` и `www.bin` (образ LittleFS). Оба собираются сервером из одного коммита. Манифест релиза подписан сервером и содержит:
- версию;
- профиль;
- SHA-256 обоих файлов;
- `www_version`, совместимую с этой прошивкой.

Порядок обновления на устройстве:
1. Устройство скачивает манифест и проверяет его подпись.
2. `app.bin` записывается в неактивный OTA-слот. Проверяются подпись (RSA-3072) и хеш из манифеста.
3. `www.bin` записывается в раздел `www`. Проверяется хеш из манифеста. Пока идёт запись, веб-морда недоступна, работает страница восстановления.
4. Только после успешной записи обоих артефактов меняется загрузочный слот и устройство перезагружается.

Если процесс прервался:
- **Сбой на шаге 2.** Ничего не изменилось, устройство остаётся на старой прошивке.
- **Сбой на шаге 3.** Старая прошивка продолжает работать, но `www` повреждён. Страница восстановления, встроенная в бинарник, предлагает повторить загрузку `www` с сервера или загрузить файл вручную.
- **Совместимость.** При старте прошивка сравнивает версию `www` (файл `www/manifest.json`) с ожидаемой `www_version`. Если они не совпадают, например после отката приложения, открывается страница восстановления с кнопкой «Скачать подходящую веб-морду».

## Раунд 7: сверка с кодом прошивки `ZIR_3M` и веб-морды `zir-web-ui`

Документы сверены с реальными репозиториями. Зафиксировано:

- **Веб-морда** доставляется архивом `www.tar`, как сейчас, а не образом LittleFS. Устройство распаковывает только архив, хеш которого подписан сервером (манифест или контейнер `.zwww`). Сырой `.tar` принимает только сборка для разработки.
- **Пароль точки доступа** пользователь может менять. Устройство сообщает новый пароль серверу, чтобы инженер мог подключиться при обслуживании.
- **Вход в веб-морду через точку доступа** — только WPA2, без отдельного пароля. Через сеть роутера — HTTP Basic, как сейчас.
- **Инженерный режим:** в боевой сборке — только через сервер. В сборке для разработки (`CONFIG_ZIR_DEV_BUILD`, PlatformIO) остаётся пункт меню прибора. Сервер не подписывает сборки для разработки.
- **Ручная загрузка `.bin`** остаётся; ставится только образ, подписанный сервером. eFuse не прожигаются.
- **Критические релизы** ставятся сразу, если заряд АКБ не ниже 20 %.
- **Жёсткие параметры:** установленные модули (FT3500, RX5808, TA8804) и их частоты. Атенюаторы и калибровка АКБ — мягкие, меняются только в инженерной сессии.
- **Телеметрия:** передаётся всё, что считает прибор (весь блок `stats`, события, сбои, журнал обнаружений). Наработка — `on_s`. Время обнаружения известно, только если прибор был в Wi-Fi с синхронизацией времени в том же запуске; иначе событие пишется без времени (номер запуска и `uptime_s`).
- **Отдельного ключа подписи для разработки нет.** Прибор с неподписанной сборкой из PlatformIO возвращается в цикл OTA перепрошивкой по USB подписанной сборкой с сервера.
- **Сборка:** проект должен собираться и PlatformIO, и `idf.py`; сервер собирает с `sdkconfig.release.defaults`; сборщику нужен доступ к реестру компонентов ESP-IDF; версия ESP-IDF сборщика совпадает с прошивкой (сейчас 6.0.1).
