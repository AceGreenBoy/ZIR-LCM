# Требования к прошивке устройства (ESP32) для работы с сервером прошивок

Документ описывает, что должна уметь прошивка, чтобы работать с сервером из `ARCHITECTURE.md`. Протоколы описаны в `ARCHITECTURE.md`, раздел 7, точные форматы запросов, подписей и шифрования — в `DEVICE_PROTOCOL.md`. Здесь — обязанности устройства.

**Платформа:** ESP32 classic, ревизия v3, 4 МБ flash, ESP-IDF 6.0.x (сейчас 6.0.1). **Уровень защиты:** L0 (eFuse не прожигаются). **Прошивка:** репозиторий `ZIR_3M` (ZIR-3M, детектор FPV-видеосигналов).

## 1. Конфигурация сборки (обязательные опции `sdkconfig`)

| Опция | Значение | Зачем |
|---|---|---|
| `CONFIG_ESP32_REV_MIN_3` | y | Нужна для схемы подписи RSA (Secure Boot V2) без аппаратного Secure Boot |
| `CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT` | y, **только в `sdkconfig.release.defaults`** | Проверять подпись образов без прожига eFuse |
| `CONFIG_SECURE_SIGNED_APPS_RSA_SCHEME` | y, только в боевой сборке | Схема RSA-3072, совместимая с будущим Secure Boot V2 (L2) |
| `CONFIG_SECURE_SIGNED_ON_UPDATE_NO_SECURE_BOOT` | y, только в боевой сборке | Принимать по OTA только подписанные образы |
| `CONFIG_SECURE_BOOT_BUILD_SIGNED_BINARIES` | **n** | Образ подписывает сервер, а не машина сборки |
| `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` | y | Автоматический откат, если новая прошивка не прошла самопроверку |
| `CONFIG_APP_REPRODUCIBLE_BUILD` | y | Сервер может определить, что код профиля не изменился |
| `CONFIG_ESP_COREDUMP_ENABLE_TO_FLASH` | y | Core dump сохраняется в раздел `coredump` |
| `CONFIG_PARTITION_TABLE_CUSTOM` | y | Таблица разделов из раздела 2 |
| `CONFIG_ESP_HTTPS_OTA_DECRYPT_CB` | y | Расшифровка образа `esp_encrypted_img` при загрузке |
| `CONFIG_ZIR_DEV_BUILD` | **n** в `sdkconfig.release.defaults`, y в окружении PlatformIO `esp32dev` | Сборка для разработки (раздел 10.1) |

**Запрещено на L0** — эти опции прожигают eFuse при первом запуске, необратимо:

| Опция | Что прожигает |
|---|---|
| `CONFIG_SECURE_BOOT` (V1 или V2) | ключ/хеш Secure Boot, `ABS_DONE_*` — перестанет запускаться неподписанный загрузчик |
| `CONFIG_SECURE_FLASH_ENC_ENABLED` | ключ и `FLASH_CRYPT_CNT` (это L1) |
| `CONFIG_BOOTLOADER_APP_ANTI_ROLLBACK` | `SECURE_VERSION` — откат на старые версии станет невозможен |
| `CONFIG_SECURE_DISABLE_ROM_DL_MODE`, `CONFIG_SECURE_UART_ROM_DL_MODE` | отключение загрузки по UART — прибор нельзя будет прошить по USB |
| `CONFIG_NVS_ENCRYPTION` с ключами в eFuse | ключ шифрования NVS (это L1) |

`CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT`, `CONFIG_ESP32_REV_MIN_3` и подпись образа сервером eFuse **не** трогают. Прошивка по USB (`esptool write_flash`) тоже. Проверка перед выпуском: `idf.py build` не выводит предупреждений о прожиге, а `espefuse.py summary` на тестовом приборе после первого запуска совпадает с исходным.

**Модули железа** включаются опциями в `Kconfig.projbuild`: `CONFIG_ZIR_MODULE_FT3500` и `CONFIG_ZIR_MODULE_TA8804`. RX5808 есть всегда. Они заменяют нынешние `BOARD_MODULE_FT3500_ENABLED` и `BOARD_MODULE_TUNER_ENABLED` в `board.h`. Профиль — файл `profiles/<code>/sdkconfig.defaults` с набором этих опций. В коде модули оборачиваются в `#ifdef CONFIG_ZIR_MODULE_<ИМЯ>`.

**Сборка на сервере запускается так:**

```
idf.py -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.release.defaults;profiles/<code>/sdkconfig.defaults" \
       -D ZIR_PROFILE=<code> -D ZIR_VERSION=<semver> build
```

- `ZIR_PROFILE` и `ZIR_VERSION` передаются в код через `CMakeLists.txt`. Версию прошивки (`PROJECT_VER`) нужно брать из `ZIR_VERSION`. Без них (локальная сборка) — `git describe`, как сейчас.
- **Проект должен собираться и PlatformIO, и `idf.py`.** Сейчас код приложения лежит в `src/`, а этот каталог как компонент подключает только PlatformIO. Для `idf.py` нужно либо переименовать `src/` в `main/` (и указать `src_dir = main` в `platformio.ini`), либо добавить `src` в `EXTRA_COMPONENT_DIRS` в корневом `CMakeLists.txt` только при сборке не из PlatformIO.
- Компонент `espressif/esp_encrypted_img` добавляется через `idf_component.yml`, версии фиксируются в `dependencies.lock`.

## 2. Таблица разделов

```
# Name,    Type, SubType,  Offset,   Size
nvs,       data, nvs,      0x9000,   0x5000
otadata,   data, ota,      0xe000,   0x2000
ota_0,     app,  ota_0,    0x10000,  0x180000
ota_1,     app,  ota_1,    0x190000, 0x180000
www,       data, littlefs, 0x310000, 0xd8000
identity,  data, nvs,      0x3e8000, 0x7000
nvs_keys,  data, nvs_keys, 0x3ef000, 0x1000
coredump,  data, coredump, 0x3f0000, 0x10000
```

**Изменения против текущей таблицы:** `www` уменьшен на 32 КБ, добавлены разделы `identity` и `nvs_keys`. Устройства со старой таблицей нужно один раз перепрошить по USB с повторной регистрацией. Для этого и для любого прибора с неизвестной разметкой есть один образ bootstrap с адреса 0x0 (`zir3m-bootstrap-<версия>.bin`, `ZIR_3M/docs/bootstrap.md`): загрузчик, таблица разделов, стёртые `nvs` и `otadata`, bootstrap в `ota_0`. `identity` он не трогает; нечитаемый `identity` прошивка стирает и регистрируется заново.

| Раздел | Содержимое | Кто пишет |
|---|---|---|
| `nvs` | Мягкие параметры, Wi-Fi (в том числе текущий пароль точки доступа), счётчик `seq` телеметрии, `release_id`, хеш `www`, сервисная статистика, журналы | Прошивка |
| `identity` | Учётные данные устройства (раздел 3) | Только bootstrap при регистрации и прошивка при получении нового конфига. OTA этот раздел не затрагивает. |
| `nvs_keys` | Пусто на L0. Резерв для шифрования NVS на L1. | — |
| `www` | Образ LittleFS с веб-мордой | Процедура обновления (раздел 6) |
| `coredump` | Core dump после сбоя | Система. Прошивка очищает раздел после отправки. |

## 3. Раздел `identity` (NVS, пространство имён `zid`)

| Ключ | Тип | Содержимое |
|---|---|---|
| `device_id` | str | UUID устройства от сервера |
| `serial` | str | Серийный номер |
| `sign_priv` | blob | Приватный ключ ECDSA P-256 (`dev_sign`), 32-байтный скаляр (формат импорта PSA) |
| `kex_priv` | blob | Приватный ключ ECDH P-256 (`dev_kex`), 32-байтный скаляр |
| `ota_key` | blob | Приватный ключ RSA-3072 для `esp_encrypted_img`, PEM. Получен от сервера и расшифрован. |
| `config` | str | Текущий подписанный конфиг (JWS) |
| `web_pass` | str | Начальный пароль `zir-XXXXX`, сгенерированный bootstrap. Текущий пароль (если пользователь его сменил) хранится в `nvs` (раздел 9). |

**Требования:**
- приватные ключи никогда не выводятся в лог, в веб-морду или в API устройства;
- при повреждении или отсутствии `identity` устройство переходит в режим регистрации (раздел 4).

## 4. Bootstrap-прошивка

Bootstrap — отдельный минимальный проект `bootstrap/` в репозитории прошивки. Он прошивается в `ota_0`. Реализация и сборка — `ZIR_3M/docs/bootstrap.md`, клиент протокола — компонент `components/lcm_client` (его же должна использовать рабочая прошивка).

**Проверка подписи.** Bootstrap собирается **без** `CONFIG_SECURE_SIGNED_APPS_*`: с ними `esp_ota_end()` отвергал бы образы без подписи, и прибор разработчика не получил бы первую dev-сборку. Подпись Secure Boot V2 устанавливаемого образа bootstrap проверяет сам, ключом `ZIR_KEYS_FWSIGN` из `zir_server_keys.h`. Проверка пропускается только для манифеста с `"dev": true` при `"dev": true` в подписанном конфиге и бите dev в `zir_custom_desc_t` образа. Загрузчик из сборки bootstrap становится загрузчиком прибора, поэтому в нём включён откат.

**Что делает bootstrap:**
0. **Проверяет заряд АКБ** при старте (как рабочая прошивка) и инициализирует экран SH1106 по I2C: код регистрации и пароль показываются на нём. Из драйверов bootstrap нужны только АКБ, I2C и SH1106.
1. **Поднимает точку доступа Wi-Fi** `ZIR3M-<последние 4 символа MAC>`.
2. **Генерирует учётные данные** (если `identity` пуст), **только после запуска Wi-Fi**. Это важно: аппаратный генератор случайных чисел ESP32 даёт полноценную энтропию только при включённом радио.
   - ключи `dev_sign` и `dev_kex` (P-256, через mbedTLS);
   - пароль `zir-XXXXX`: 5 символов из алфавита без похожих знаков `23456789ABCDEFGHJKMNPQRSTUVWXYZ`.
3. **Защищает точку доступа** паролем `zir-XXXXX` (WPA2, 9 символов). Пароль показывается на экране устройства.
4. **Отдаёт встроенную мини-страницу**: ввод SSID и пароля Wi-Fi объекта, статус и код регистрации. `www` не используется.
5. **Регистрируется на сервере** после подключения к Wi-Fi (`POST /dev/v1/register/request`, `ARCHITECTURE.md` 7.2). Затем показывает `claim_code` на экране и на мини-странице и опрашивает `GET /dev/v1/register/status` каждые 5 секунд.
6. **После подтверждения** производителем:
   - проверяет подпись конфига (`K_config`) и совпадение `device_id` и MAC;
   - расшифровывает `ota_key` своим `dev_kex`;
   - записывает всё в `identity`.
7. **Ставит рабочую прошивку и веб-морду** через обычную процедуру обновления (раздел 6) и перезагружается в рабочую прошивку. Обычную прошивку — при заряде от 20 % или при питании от USB без АКБ; dev-сборку — без проверки заряда.
8. **Передаёт рабочей прошивке** (NVS `nvs`):
   - пространство `wifi`: `sta_ssid`, `sta_pass` и `ap_pass` = `zir-XXXXX` (ключи `wifi_service`);
   - пространство `lcm`: `pend_release`, `pend_devbuild`, `pend_mode`, `app_sha256`, `www_sha256`.

   После самопроверки рабочая прошивка отправляет по этим данным отчёт `installed` (раздел 6.2, шаг 5). Сам bootstrap отправляет только `downloading` и `failed`.

Bootstrap не содержит секретов, только публичные ключи сервера.

**Регистрация из рабочей прошивки.** Если `identity` пуст (прибор прошит рабочей прошивкой по USB), рабочая прошивка регистрируется сама, как bootstrap, когда есть сеть с интернетом. Код показывается в меню («LCM»), на экране блокировки сборки для разработки и в веб-морде (`registration` в `/api/info`). Общий пароль точки доступа `zir3m-admin` при этом заменяется собственным `zir-XXXXX`.

**Если `identity` уже заполнен и валиден** (прибор перепрошили по USB, например чтобы вернуть его из сборки для разработки), bootstrap не регистрируется заново: он подключается к сохранённому Wi-Fi и сразу переходит к шагу 7. Поэтому скрипт `flash.sh`/`flash.bat` в пакете производителя пишет только загрузчик, таблицу разделов, `otadata` и bootstrap и **не стирает flash целиком**. Для полной перерегистрации есть отдельный ключ скрипта `--erase`.

## 5. Связь с сервером

- **Адрес сервера** зашит в прошивку: `https://fw.<домен>`.
- **TLS:** `esp_http_client` или `esp_https_ota` с закреплёнными корневыми сертификатами ISRG Root X1 и ISRG Root X2. Общий бандл сертификатов не используется.
- **Время:** после подключения к Wi-Fi синхронизировать SNTP. Время нужно для `device_time` в телеметрии и проверки срока действия манифестов и токенов. Если время ещё не синхронизировано, срок действия проверяется по времени сервера из ответа (заголовок `Date`).
- **Аутентификация** — challenge-response (`ARCHITECTURE.md` 7.1). При аутентификации сообщаются MAC (из eFuse, `esp_efuse_mac_get_default`) и `app_sha256` текущей прошивки.
- **Публичные ключи сервера** вкомпилированы в прошивку в формате PEM: `K_manifest`, `K_config`, `K_engtoken`, `K_www`, `K_telemetry`.
  - Должна поддерживаться **таблица ключей**: несколько ключей на одно назначение и выбор по `kid` из заголовка JWS. Это нужно для смены ключей.
- **Повторные попытки:** экспоненциальная пауза от 5 секунд до 10 минут. Отсутствие связи — штатная ситуация, устройство должно полностью работать офлайн.

## 6. Обновления

### 6.1 Проверка

- `GET /dev/v1/update` вызывается при каждом подключении к сети и затем через `poll_after` секунд из ответа (6 часов, прибор разработчика — 30 с). Реализация клиента — `components/lcm_service` в `ZIR_3M` (меню «LCM» и «Оновлення», `POST /api/update/check|install`).
- Если `config_version` в ответе больше своей, сначала забрать новый конфиг, а уже потом проверять манифест: от конфига зависит, допустим ли манифест с `"dev": true`.
- Манифест с `"dev": true` боевая прошивка не ставит: `esp_ota_end()` отверг бы образ без подписи. Прибор показывает «Збірку розробника можна встановити лише по USB».
- **Отчёт после установки.** Перед перезагрузкой в NVS `lcm` записывается `pend_*`, в том числе `pend_slot` — раздел, назначенный загрузочным. После самопроверки новая прошивка сравнивает `pend_slot` с текущим разделом: совпадает — `installed`, нет (загрузчик откатил) — `rolled_back`. Так же отчитывается установка, сделанная bootstrap.
- **Ответ `403 device_revoked`:** устройство показывает «Обновления недоступны» и больше не запрашивает обновления до следующей перезагрузки. Телеметрию продолжает отправлять. Отзыв запоминается в NVS (`lcm`/`revoked`): после перезагрузки статус «отозван» (и блокировка сборки для разработки) действует сразу, до связи с сервером. Одна проверка после загрузки разрешена: если отзыв сняли, признак стирается и блокировка снимается.
- **Проверка манифеста.** Устройство отклоняет манифест, если не выполняется хотя бы одно условие:
  - подпись `K_manifest` верна;
  - `device_id` совпадает со своим;
  - `profile` совпадает с профилем, вкомпилированным в прошивку;
  - `exp` ещё не наступил.
- **Режимы:**
  - `mode=button` — показать пользователю кнопку «Обновить» (на экране и в веб-морде). Установка по кнопке — при заряде АКБ не ниже 30 % (как сейчас в `web_ota.c`);
  - `mode=auto` (критический релиз) — ставить сразу, если заряд АКБ не ниже 20 %. Иначе показать «Потрібне оновлення, зарядіть прилад» и поставить, когда заряд поднимется до 20 %;
  - `mode=engineer` — ставить сразу, это назначение инженера (порог 30 %).
- **Ресурсы.** Свободной кучи у прибора около 80 КБ, а TLS, RSA-3072 и расшифровка образа требуют много памяти. На время загрузки сканирование ставится на паузу, на экране показывается полоса прогресса.

### 6.2 Установка (порядок обязателен)

1. **`app`** (если `needed`): `esp_https_ota` с `decrypt_cb` из компонента `esp_encrypted_img`, ключом `ota_key`, в неактивный слот.
   - `esp_https_ota_finish` проверяет подпись RSA-3072.
   - Дополнительно сверяется SHA-256 расшифрованного образа с манифестом.
   - Проверяется, что встроенное описание профиля (раздел 6.4) совпадает с профилем устройства.
   - Слот загрузки пока **не переключается**.
2. **`www`** (если `needed`), архив `www.tar`:
   - удалить маркер `/www/.valid` и отформатировать раздел (как сейчас в `POST /api/www`);
   - распаковывать архив потоково, одновременно считая SHA-256 всего архива. Отклонять пути с `..`, абсолютные пути, ссылки и всё, кроме обычных файлов и каталогов;
   - в конце сверить SHA-256 с манифестом, затем прочитать `manifest.json` и сверить `version` и `www_api`;
   - только после этого записать маркер `/www/.valid`.
   - **Без маркера файлы из `www` не отдаются**, работает страница восстановления. Так неподтверждённое содержимое не будет открыто в браузере, даже если распаковка оборвалась на середине.
3. **Переключение:** `esp_ota_set_boot_partition` для нового слота, сохранить в NVS `pending_release_id`, перезагрузиться.
4. **Самопроверка новой прошивки** до `esp_ota_mark_app_valid_cancel_rollback()`:
   - `identity` читается;
   - конфиг валиден;
   - `www` монтируется;
   - веб-сервер стартует.
   Наличие связи с сервером в самопроверку **не входит**: устройство может быть офлайн. Если самопроверка не прошла — `esp_restart()`, и загрузчик откатит прошивку.
5. **Отчёт.** `POST /dev/v1/update/report` со статусом `installed`, `failed` или `rolled_back`. Отчёт отправляется при следующей связи с сервером, если сейчас её нет. После успеха `pending_release_id` записывается в `release_id`.

**Сбои:**
- **Сбой на шаге 1:** ничего не меняется.
- **Сбой на шаге 2:** прошивка остаётся старой, `www` повреждён. Работает страница восстановления (раздел 7), в ней кнопка «Загрузить веб-морду с сервера».
- Если прошивка откатилась после того, как `www` уже обновлён, `www_api` не совпадёт. Прошивка обнаружит это при старте (раздел 7).

### 6.3 Совместимость прошивки и веб-морды

- Прошивка содержит константу `ZIR_WWW_API` (целое число). Её увеличивают при несовместимом изменении API устройства для веб-морды.
- При старте прошивка читает `/www/manifest.json` (несжатый, рядом не должно быть `.gz`-версии). Если `www_api` не совпадает, файла или маркера `/www/.valid` нет, вместо веб-морды открывается страница восстановления.

### 6.4 Встроенное описание профиля

В прошивке объявляется структура в секции `.rodata_custom_desc`. ESP-IDF размещает её сразу после `esp_app_desc_t`, и сервер читает её из образа при сборке.

```c
typedef struct {
    uint32_t magic;          // 0x5A495244 'ZIRD'
    uint16_t desc_version;   // 1
    uint16_t www_api;        // ZIR_WWW_API
    char     profile[32];    // ZIR_PROFILE
    char     version[32];    // ZIR_VERSION
    uint32_t flags;          // бит 0 ZIR_DESC_FLAG_DEV_BUILD = CONFIG_ZIR_DEV_BUILD
    uint8_t  reserved[52];
} zir_custom_desc_t;         // 128 байт

const __attribute__((section(".rodata_custom_desc")))
zir_custom_desc_t zir_custom_desc = { ... };
```

## 7. Страница восстановления

- **Встроена в бинарник прошивки** (`EMBED_FILES`), не зависит от `www`.
- **Открывается**, если `www` не монтируется, нет `manifest.json` или не совпадает `www_api`. Также всегда доступна по адресу `/recovery`.
- **Доступ** — как у веб-морды (раздел 9).
- **Умеет:**
  - «Загрузить веб-морду с сервера»: запрашивает `GET /dev/v1/update`, затем скачивает только `www`, подходящий для текущей прошивки;
  - «Загрузить веб-морду из файла»: боевая сборка принимает **только** контейнер `.zwww` (`ARCHITECTURE.md` 7.8). Сначала проверяется подпись заголовка `K_www` и `www_api`, затем архив распаковывается с проверкой SHA-256 (раздел 6.2). Сырой `www.tar` принимает только сборка для разработки;
  - «Загрузить прошивку из файла» (`app.bin`, как сейчас `POST /api/ota`): остаётся в любой сборке. `esp_ota_end` проверяет подпись RSA-3072, поэтому ставится только образ, подписанный сервером. Порог заряда — 30 %.

## 8. Конфиг устройства

- **Жёсткие параметры** — установленные модули (`ft3500`, `rx5808`, `ta8804`) и их частоты (min/max, МГц). Они берутся **только** из подписанного конфига в `identity`. Сканирование, ручная настройка (`POST /api/tune`) и границы в веб-морде ограничиваются этими частотами. Модуль, которого нет в конфиге, считается неустановленным (`fitted: false`).
- **При старте конфиг проверяется:**
  - подпись `K_config` верна;
  - `device_id` и `mac` совпадают с устройством;
  - `profile` совпадает со встроенным.
- **Если конфиг невалиден, устройство переходит в безопасный режим:**
  - модули железа не активируются, выходы в безопасном состоянии;
  - на экране и в веб-морде показывается ошибка;
  - продолжают работать связь с сервером, проверка обновлений, вход инженера и страница восстановления.
- **Новый конфиг** принимается, только если его `version` больше текущей.
  - Сначала он записывается во временный ключ, проверяется и только потом заменяет текущий.
  - Модули, которых нет в прошивке профиля, но которые включены в конфиге, игнорируются, а в журнал пишется предупреждение.
- **Мягкие параметры** хранятся в `nvs` без подписи и меняются локально. Они делятся на две группы:
  - **пользовательские:** включение диапазонов `band_*`, яркость, звук захвата, мощность Wi-Fi и т. п.;
  - **инженерные:** атенюаторы `atten_*`, калибровка АКБ `bat_cal` и `bat_sag_mv`, кривая разряда, параметры детектора (`smp_count`, `sync_min`, `lock_hits`, `unlock_miss`, `hold_s`). `PUT /api/settings` меняет их только в инженерной сессии, иначе `403`. `GET /api/settings` должен помечать такие ключи (например, полем `"eng": true`), чтобы веб-морда показывала их только в инженерном разделе.
- **Получение конфига:** если в ответе `GET /dev/v1/update` `config_version` больше текущей, устройство вызывает `GET /dev/v1/config`.

## 9. Веб-морда устройства и пароль

- **Пароль.** Один пароль используется для точки доступа (WPA2) и для входа в веб-морду через сеть роутера. Начальный — `zir-XXXXX` из `identity`, он показывается на экране в меню Wi-Fi. Общий пароль `zir3m-admin` из нынешней прошивки убирается.
- **Смена пароля** пользователем (`PUT /api/wifi {ap_password}`) остаётся. Новый пароль сохраняется в `nvs`, ставится флаг «не отправлен», и при ближайшей связи пароль уходит на сервер (`POST /dev/v1/web-password`, `ARCHITECTURE.md` 7.10). На экране показывается текущий пароль.
- **Доступ:**
  - через точку доступа устройства пароль веб-морды не спрашивается, достаточно WPA2 (как сейчас);
  - через сеть роутера — HTTP Basic с паролем точки доступа (как сейчас), для WebSocket — `?key=`;
  - **блокировка:** после 5 неудачных попыток — пауза 5 минут. Счётчик общий для устройства, не по IP.
- **`GET /api/info`** дополнительно возвращает `version` (semver), `www_api`, профиль, установленные модули и их частоты из конфига, состояние конфига (валиден или безопасный режим), сборку для разработки (`dev_build`), статус обновлений (есть ли предложение, его версия, критическое ли, отложено ли из-за заряда, отозвано ли устройство) и статус связи с сервером.
- **`POST /api/update/check`** и **`POST /api/update/install`** — проверка и установка по кнопке пользователя.
- **Контракт для веб-морды** с точными форматами — `docs/web-ui-brief.md` в репозитории прошивки, раздел «Изменения для сервера прошивок». Коротко, что добавляется в API прибора:
  - в `/api/info`: `version`, `www_api`, `profile`, `serial`, `dev_build`, `config {valid, version, modules}`, `server {state, last_seen}`, `update {state, version, critical, mode, deferred, percent}`;
  - в `state`: `eng_session {name, expires_in}` в инженерной сессии и `upload.kind = "server"` при установке с сервера;
  - в `/api/settings`: признак `"eng": true` у инженерных ключей;
  - в `/api/log` и CSV: поле `time` (Unix UTC или `null`, см. раздел 11);
  - `POST /api/www` принимает `.zwww` (по сигнатуре `ZWWW`), а сырой `.tar` — только в сборке для разработки;
  - `POST /eng/logout`;
  - новые ошибки: `429 too many attempts`, `403 engineer session required`, `409 no update`, `409 battery below 20%`, `400 not a signed www container`, `400 www_api mismatch`.

## 10. Инженерный вход

Протокол описан в `ARCHITECTURE.md` 7.4.

### 10.1 Боевая сборка и сборка для разработки

| | Боевая (`CONFIG_ZIR_DEV_BUILD=n`) | Для разработки (`CONFIG_ZIR_DEV_BUILD=y`) |
|---|---|---|
| Кто собирает | Сервер | Разработчик в PlatformIO (`pio run -e esp32dev`) |
| Вход в инженерный режим | Только по токену сервера (раздел 10.2) | Также пункт меню прибора «Інженерний режим» (как сейчас) |
| Ручная загрузка `www` | Только `.zwww` | `.zwww` и сырой `www.tar` |
| Подпись сервером | Да | Сервер отказывается подписывать |
| Как попадает на устройство | OTA, ручная загрузка `.bin` | По USB; по OTA — только на прибор разработчика (`"dev": true` в конфиге) |
| Wi-Fi при включении | Выключен, включается в меню | **Включён** |
| Работа без сервера | Без ограничений | **Не больше часа наработки** без синхронизации, затем обнаружение останавливается |
| Проверка подписи при OTA | Да: только образы, подписанные сервером | Нет: принимает любой `.bin` (как сейчас) |

- **Проверка подписи включена только в боевой сборке.** Прибор проверяет новый образ ключом из подписи **текущей** прошивки. У сборки для разработки подписи нет, и с включённой проверкой она не приняла бы никакой образ. Без проверки на приборе со сборкой для разработки работает ручная загрузка любого `.bin`, в том числе подписанной боевой сборки. После её установки прибор принимает только подписанные образы.
- Пошаговое задание для репозитория прошивки — `docs/lcm-build.md` в `ZIR_3M`.
- Пункт меню «Інженерний режим» и приём сырого `www.tar` компилируются только под `#ifdef CONFIG_ZIR_DEV_BUILD`.
- Устройство со сборкой для разработки показывает это на экране и в веб-морде (`dev_build: true` в `/api/info`).
- **Ограничение сборки для разработки** (реализация — `components/lcm_service` в `ZIR_3M`):
  - **Синхронизация** — сессия с сервером (`auth/session` и `GET /update`), при которой подписанный конфиг прибора содержит `"dev": true`. В NVS (`lcm`) запоминаются `STAT_ON_S` и `STAT_BOOTS` на этот момент.
  - **Наработка с последней синхронизации** = прирост `STAT_ON_S` плюс 60 с за каждое включение. Добавка за включение нужна, потому что `STAT_ON_S` сохраняется раз в минуту, и частое выключение питания иначе растягивало бы час. Часы реального времени не используются, их у прибора нет.
  - **Час наработки без синхронизации** — обнаружение останавливается. Экран показывает «ПРИЛАД ЗАБЛОКОВАНО» и причину. Если прибор не зарегистрирован — ещё код регистрации, если нет сети — подсказку про Wi-Fi. В веб-морде — красная плашка (`dev_limit` в `/api/info` и `state`). Wi-Fi остаётся включённым, меню доступно. После первой удачной синхронизации прибор снова работает.
  - **Сразу, без ожидания часа**, обнаружение останавливается, если сервер отозвал прибор или в подписанном конфиге нет `"dev": true`. Отозванный прибор заблокирован и после перезагрузки — с первого экрана, не дожидаясь сервера (раздел 6.1).
  - **Незарегистрированный прибор** (плата прошита по USB, `identity` нет) получает первый час с момента первого запуска сборки для разработки. Регистрируется он прямо из рабочей прошивки (раздел 4, «Регистрация из рабочей прошивки»). Чтобы работать дольше, его нужно зарегистрировать как прибор разработчика.
- **Возврат в обычный цикл обновлений.** Прибор со сборкой для разработки переводится на боевую прошивку ручной загрузкой подписанного `app.bin` (через `/recovery`) или по USB. `identity` при этом сохраняется, повторная регистрация не нужна. Обратно, на сборку для разработки, — только по USB.

### 10.2 Вход через сервер

- **`GET /eng/start`:**
  - сгенерировать `nonce` (16 байт `esp_random`);
  - запомнить его в RAM на 5 минут (не больше 4 одновременно, старые вытесняются);
  - перенаправить на `https://fw.<домен>/eng/login?device=<id>&nonce=<n>&return=http://<свой IP>/eng/callback`.
- **`GET /eng/callback`** отдаёт встроенную страницу, которая берёт `token` из fragment и отправляет его на `POST /eng/session`.
- **`POST /eng/session` проверяет токен:**
  - подпись `K_engtoken` верна;
  - `dev` совпадает с `device_id` устройства;
  - `nonce` есть в списке выданных (после проверки удаляется — токен одноразовый);
  - `exp` ещё не наступил;
  - если есть связь с сервером — `POST /dev/v1/engineer/confirm {jti}`, а отказ сервера означает отказ во входе.
- **Инженерная сессия:**
  - отдельная cookie;
  - длится не больше 30 минут;
  - при наличии связи с сервером каждые 5 минут вызывается `confirm`; ответ `403` закрывает сессию сразу.
- **Возможности инженерной сессии:**
  - просмотр инженерных данных (осциллограмма, лог ESP, тайминги скана — нынешние `/api/eng/*`);
  - изменение инженерных мягких параметров (атенюаторы, калибровка и кривая разряда АКБ, параметры детектора);
  - запрос на изменение жёстких параметров (`POST /dev/v1/config/request` или передача через браузер, `ARCHITECTURE.md` 7.5);
  - проверка и установка назначенной версии.
- **Журнал действий инженера** хранится в `nvs`: время, `engineer_id`, действие. Он отправляется в составе телеметрии (`engineer_audit`) и очищается после подтверждения сервером.

## 11. Телеметрия и core dump

- **Конверт пакета** — `ARCHITECTURE.md` 7.6: ECDH P-256 с эфемерным ключом, HKDF-SHA256, AES-256-GCM, подпись ECDSA `dev_sign`. Всё на mbedTLS.
- **`seq`** — монотонный счётчик в `nvs`, увеличивается **до** отправки и сохраняется сразу. Номера не переиспользуются, даже если отправка не удалась.
- **Отправка** — при каждом подключении к серверу. Как копить данные офлайн (объём и период), решает прошивка. Ограничение: накопленная телеметрия не должна вытеснять журнал действий инженера.
- **Состав:** передаётся вся телеметрия прибора:
  - обязательные поля `seq`, `device_time`, `uptime_s`, `app_version`, `release_id`;
  - весь блок `stats` (`service_stats`): наработка `on_s` (её сервер отслеживает на уменьшение), `screen_s`, `wifi_s`, `boots`, `rst_*`, ошибки I2C и АЦП, `amt_boot_*`, `bat_deep`, `selftest_*`; новые ключи добавляются автоматически;
  - `reset_reason`, `heap_min`;
  - события: обнаружения, `battery_low`, смена режима. У прибора нет часов реального времени, поэтому каждое событие записывается с номером запуска (`boot`, счётчик `boots`) и `uptime_s` на момент события. Поле `time` (UTC) заполняется, только если время было синхронизировано по SNTP. Если синхронизация случилась позже в том же запуске, прибор досчитывает `time` для накопленных событий этого запуска: `time = now − (uptime_now − uptime_s)`. События без времени тоже отправляются;
  - `engineer_audit`.
- **Core dump:** если при старте в разделе `coredump` есть валидный дамп, при ближайшей связи он отправляется (`POST /dev/v1/coredump`, такой же конверт). После ответа `200` сводка сбоя (задача, причина, backtrace) сохраняется в `nvs`, чтобы её по-прежнему было видно в `/api/info`, а раздел очищается (`esp_core_dump_image_erase`).

## 12. Общие требования безопасности

- Не логировать ключи, пароль `zir-XXXXX`, токены и содержимое `identity`.
- Все входные данные из сети (манифест, конфиг, токены, загружаемые файлы) проверяются по подписи **до** разбора полей, которые влияют на поведение устройства.
- Веб-сервер устройства ограничивает размер тела запроса. Исключение — загрузка `.zwww`, которая пишется потоково.
- Не использовать прямое чтение и запись flash в обход API разделов. Иначе на L1 (Flash Encryption) код сломается.
- Готовность к L1: шифрование NVS через `nvs_keys` должно включаться опцией конфигурации без изменений в коде.

## 13. Чек-лист приёмки прошивки

- [ ] Образ, подписанный чужим ключом, отклоняется при OTA.
- [ ] Образ, зашифрованный для другого устройства, не устанавливается.
- [ ] Манифест чужого устройства, чужого профиля или с истёкшим сроком отклоняется.
- [ ] Повреждённый `www` приводит на страницу восстановления. Восстановление с сервера и из `.zwww` работает. Неподписанный `.zwww` отклоняется.
- [ ] Откат прошивки после неудачной самопроверки срабатывает, отчёт `rolled_back` доходит до сервера.
- [ ] Конфиг с неверной подписью или чужим MAC переводит устройство в безопасный режим.
- [ ] Токен инженера нельзя использовать повторно, на другом устройстве и после истечения срока.
- [ ] Отзыв инженера на сервере закрывает его сессию на устройстве в течение 5 минут (вариант «а»).
- [ ] Отозванное устройство не получает обновления, но продолжает отправлять телеметрию.
- [ ] Повтор пакета телеметрии отклоняется сервером.
- [ ] Устройство полностью работает без интернета.
- [ ] Боевая сборка не имеет пункта меню «Інженерний режим» и не принимает сырой `www.tar`.
- [ ] Неподписанный `.bin` (сборка PlatformIO) не устанавливается через `/api/ota` на приборе с подписанной прошивкой.
- [ ] Оборванная или подменённая распаковка `www` не открывается в браузере (нет маркера `.valid`), работает страница восстановления.
- [ ] Критический релиз не ставится при заряде ниже 20 % и ставится после зарядки.
- [ ] Смена пароля точки доступа доходит до сервера при следующей связи.
- [ ] Инженерные настройки нельзя изменить без инженерной сессии.
- [ ] Прибор собирается и PlatformIO, и `idf.py` с профилем.
