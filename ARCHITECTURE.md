# ZIR LCM (LifecycleManager): архитектура сервера прошивок и лицензий для устройств ESP32

Документ описывает сервер: что он хранит, какие протоколы обслуживает и как развёртывается. Требования к прошивке устройства вынесены в отдельный документ `FIRMWARE_REQUIREMENTS.md`. История обсуждения и обоснования решений лежат в `ARCHITECTURE_DRAFT.md`. Точные форматы протокола устройства — `DEVICE_PROTOCOL.md`, реализация — `lcm/`.

## 1. Назначение и границы

Сервер решает такие задачи:

1. **Регистрирует устройства.** Новое устройство попадает в БД только через производителя (`manufacturer`).
2. **Выдаёт прошивки.** Прошивка собирается под профиль железа устройства, шифруется персональным ключом устройства и подписывается. Выдаётся только зарегистрированным и не отозванным устройствам.
3. **Управляет доступом инженеров к инженерному меню.** Доступ подтверждается онлайн через сервер, лицензию инженера можно отозвать.
4. **Хранит и подписывает конфиг железа** (жёсткие параметры: установленные модули и диапазоны).
5. **Собирает прошивки и веб-морду** из GitHub, ведёт каналы `beta` и `stable`, поддерживает критические релизы.
6. **Принимает телеметрию и core dump**, проверяет подпись и расшифровывает. Обнаруживает аномалии: признаки клонов и скрученного счётчика наработки.
7. **Ведёт журнал аудита** всех значимых действий.

**Устройство:** ZIR-3M — портативный детектор FPV-видеосигналов. Приёмные модули: FT3500 (3,3 ГГц), RX5808 (5,8 ГГц), TA8804 (1,2 ГГц). Прошивка — репозиторий `ZIR_3M`, веб-морда — репозиторий `zir-web-ui`.

**Целевая платформа устройства:** ESP32 classic (WROOM, 4 МБ flash, ревизия v3), ESP-IDF 6.0.x. Версия ESP-IDF в образе сборщика должна совпадать с версией, которой собирается прошивка (сейчас 6.0.1, см. `dependencies.lock` прошивки).

**Масштаб:** до 10 пользователей сервера, сотни устройств. Архитектура рассчитана на рост до десятков тысяч устройств без смены подхода.

## 2. Уровень защиты и модель угроз

Система проектируется под три уровня. Сейчас реализуется **L0**. Сервер с самого начала поддерживает всё необходимое для L1 и L2, и переход на них не требует его переделки.

| Уровень | На устройстве | Статус |
|---|---|---|
| **L0** | Без прожига eFuse. Прошивка, полученная по OTA, проверяется по подписи (RSA-3072). Образ шифруется под каждое устройство. Конфиг подписан. Запросы к серверу подписываются ключом устройства. | **Реализуется сейчас** |
| **L1** | L0 и Flash Encryption с ключом от сервера, режим Development. Перепрошивка по UART остаётся возможной. | По решению бизнеса |
| **L2** | L1 и Secure Boot V2, режим Release | Опционально |

### Что защищено на L0

- **Незарегистрированное устройство** (клон, самоделка) не получит ни прошивку, ни конфиг. Регистрирует только производитель по коду с экрана устройства.
- **Перехваченный образ прошивки** бесполезен: он зашифрован персональным ключом конкретного устройства.
- **Подменить прошивку через OTA нельзя:** устройство принимает только образы, подписанные ключом подписи прошивок.
- **В инженерное меню нельзя войти без действующей учётки инженера на сервере.** Отзыв вступает в силу не позже чем через 30 минут.
- **Отозванное устройство** больше не получает обновлений.
- **Телеметрию** нельзя прочитать при перехвате и нельзя незаметно подделать.

### Что НЕ защищено на L0 (закрывается на L1)

- **Чтение flash по USB.** Человек с USB-UART может считать flash и получить открытым текстом прошивку, ключи устройства и конфиг. С этими данными он может сделать клон, который представится оригиналом.
  - Сервер такие клоны **обнаруживает, но не предотвращает**: одно устройство выходит на связь с разных адресов, номера пакетов телеметрии повторяются, сообщённый MAC не совпадает с записанным.
- **Правка памяти по USB.** Можно изменить счётчик наработки до отправки на сервер. Сервер обнаружит уменьшение счётчика, но не предотвратит его.
- **Перепрошивка по USB** любой прошивкой возможна. Это сознательное решение, чтобы не испортить устройства на этапе обкатки.

## 3. Роли и права

Учётки на сервере есть только у людей. Устройства аутентифицируются своими ключами. Пользователь устройства не имеет учётки на сервере. Он подключается к точке доступа устройства по паролю WPA2. Начальный пароль `zir-XXXXX` генерирует bootstrap. Пользователь может его сменить, и устройство сообщает новый пароль серверу (раздел 7.10), чтобы инженер мог подключиться к устройству при обслуживании.

| Действие | superadmin | admin | manufacturer | engineer |
|---|:-:|:-:|:-:|:-:|
| Просмотр устройств, телеметрии, истории обновлений | ✓ | ✓ | ✓ | ✓ |
| Регистрация нового устройства (ввод кода и профиля) | ✓ | | ✓ | |
| Вход в инженерное меню устройства | ✓ | | | ✓ |
| Изменение жёстких параметров конфига | ✓ | | | ✓ |
| Установка любой версии на устройство (в том числе `beta` и откат) | ✓ | | | ✓ |
| Закрепление версии, пометка устройства как тестового | ✓ | | | ✓ |
| Скачивание core dump и ELF для разбора | ✓ | | | ✓ |
| Запуск сборки, создание релиза, перевод в `stable`, пометка «критический» | ✓ | | | |
| Отзыв и восстановление устройств | ✓ | | | |
| Управление пользователями, ролями и лицензиями (отзыв инженеров и производителей) | ✓ | | | |
| Управление профилями железа | ✓ | | | |
| Приборы разработчика: флаг `dev`, сборки для разработки, токены API | ✓ | | | |
| Просмотр журнала аудита | ✓ | ✓ | | |

- Одному пользователю можно выдать несколько ролей, например `manufacturer` и `engineer`.
- **Доступ инженера** сейчас распространяется на все устройства. Модель данных позволяет позже ограничить его группами устройств (раздел 15).

**Отзыв пользователя** (статус `revoked`):
- немедленно завершаются все его сессии в админке;
- он больше не может войти;
- инженерные токены ему больше не выдаются;
- регистрации от его имени больше не принимаются.

Устройства, которые он успел зарегистрировать, остаются действующими. Отзыв каскадом не применяется: при необходимости устройства отзываются по одному.

### Почему модульный монолит

При 10 пользователях и сотнях устройств отдельные микросервисы только усложнят развёртывание. Модули разделены на уровне Go-пакетов с явными интерфейсами. При росте любой модуль можно вынести в отдельный сервис.

### Почему сборщик отделён

- Сборка ESP-IDF тяжёлая (2–4 ГБ RAM) и выполняет чужой код из репозитория (скрипты CMake, npm).
- Поэтому сборщик работает в отдельном контейнере с ограничениями по памяти и CPU, без доступа к ключам.
- Он только собирает **неподписанные** артефакты. Подписывает их `lcm`.

## 5. Ключи и секреты

| Ключ | Алгоритм | Где хранится | Назначение |
|---|---|---|---|
| **Мастер-ключ** | AES-256 | Файл `/run/secrets/master.key` на VPS. **Офлайн-копия обязательна.** | Envelope encryption всех секретов в БД |
| **Ключ подписи прошивок** | RSA-3072 | В БД, зашифрован мастер-ключом. **Офлайн-копия обязательна.** | Подпись `app.bin` (формат блока подписи Secure Boot V2) |
| `K_manifest` | ECDSA P-256 | БД, зашифрован | Подпись манифестов обновлений |
| `K_config` | ECDSA P-256 | БД, зашифрован | Подпись конфигов устройств |
| `K_engtoken` | ECDSA P-256 | БД, зашифрован | Подпись токенов инженера |
| `K_www` | ECDSA P-256 | БД, зашифрован | Подпись контейнера `www` для ручной загрузки через страницу восстановления |
| `K_telemetry` | ECDH P-256 | БД, зашифрован | Расшифровка телеметрии и core dump |
| Ключ подписи устройства `dev_sign` | ECDSA P-256 | Приватный — на устройстве; публичный — в БД | Аутентификация устройства, подпись телеметрии |
| Ключ обмена устройства `dev_kex` | ECDH P-256 | Приватный — на устройстве; публичный — в БД | Защищённая доставка персональных ключей на устройство |
| `K_ota` устройства | RSA-3072 (схема `esp_encrypted_img`) | Генерируется сервером при регистрации. Хранится в БД зашифрованным мастер-ключом. На устройство доставляется зашифрованным под `dev_kex`. | Шифрование образа прошивки под конкретное устройство |
| `K_flash` устройства (L1) | AES-256 | Генерируется при переходе на L1, хранится в БД зашифрованным | Flash Encryption. Сейчас не используется, поле зарезервировано. |
| Пароли пользователей | argon2id | БД | |
| Секреты TOTP | | БД, зашифрованы мастер-ключом | |
| Пароль точки доступа и веб-морды устройства | | БД, зашифрован мастер-ключом. Начальный приходит при регистрации, текущий — от устройства после каждой смены (7.10). | Показывается инженеру в админке для обслуживания устройства |

### Правила обращения с ключами

- **Публичные ключи сервера** (`K_manifest`, `K_config`, `K_engtoken`, `K_www`, `K_telemetry`) **вкомпилированы в прошивку**. Сама прошивка подписана, поэтому подменить эти ключи нельзя. Смена ключей сервера проводится так:
  1. Выпустить прошивку, которая знает и старый, и новый ключ.
  2. Дождаться, пока устройства обновятся.
  3. Переключить подпись на новый ключ.
- **Ключ подписи прошивок — самый ценный.** В режиме проверки подписи без Secure Boot устройство проверяет новый образ публичным ключом из подписи **текущей** прошивки.
  - **Потеря ключа** означает, что ни одно устройство больше нельзя обновить по OTA, только перепрошивкой по USB.
  - **Утечка ключа** позволит подписать чужую прошивку.
  - Поэтому: офлайн-копия в двух местах (зашифрованная флешка и бумажная копия в сейфе). Доступ к экспорту только у `superadmin` через CLI на сервере, не через веб-интерфейс.
- **Расшифрованные приватные ключи** живут только в памяти процесса `lcm`, в модуле `signer`. Другие модули получают только операции «подписать» и «расшифровать», но не сами ключи.
- **Мастер-ключ хранится отдельно от БД.** Бэкап БД без мастер-ключа бесполезен для злоумышленника. Мастер-ключ хранится офлайн отдельно от бэкапов.

```sql
)
```

**Журнал аудита только дописывается.** У роли БД, под которой работает `lcm`, на таблицу `audit_log` есть только `INSERT` и `SELECT`, без `UPDATE` и `DELETE`.

## 7. Протоколы

Все взаимодействия идут по HTTPS через Traefik. Устройство проверяет сертификат сервера по закреплённым корневым сертификатам Let's Encrypt: ISRG Root X1 и ISRG Root X2.

**Форматы подписей.** Все подписи сервера и устройства — ECDSA P-256 + SHA-256 в формате JWS compact (`ES256`). Исключение — подпись образа прошивки (RSA-3072, формат ESP-IDF). JWS выбран потому, что он стандартный, хорошо поддержан в Go и легко разбирается на устройстве через mbedTLS: base64url и JSON.

### 7.1 Аутентификация устройства

Устройство не использует mTLS: Traefik терминирует TLS. Вместо этого устройство получает короткую сессию по схеме challenge-response.

```
ESP32                                           lcm
  │ POST /dev/v1/auth/challenge {device_id} ─►│ проверяет, что device_id существует
  │◄──────────────── {nonce, expires_in: 60} ─│ сохраняет nonce
  │ POST /dev/v1/auth/session                 │
  │   {device_id, nonce, mac, app_sha256,     │
  │    sig = ES256(dev_sign, всё выше)} ─────►│ проверяет подпись ключом dev_sign_pub,
  │                                           │ одноразовость nonce, MAC
  │◄──── {session_token, expires_in: 900} ────│
  │ далее: Authorization: Bearer <token>      │
```

- **Отозванное устройство** сессию получает: телеметрия от него нужна для расследования. Ограничения применяются в конкретных эндпоинтах (раздел 7.9).
- **Неизвестный `device_id` или неверная подпись** дают ответ `401` и запись в `anomalies`, если `device_id` известен.
- **Несовпадение MAC** с записанным в БД: сессия выдаётся, но фиксируется аномалия `mac_mismatch`.
- **Две активные сессии одного устройства с разных IP** фиксируются как аномалия `concurrent_sessions` (признак клона).

### 7.2 Регистрация (первая прошивка)

```
Производитель      ESP32 (bootstrap)                 lcm              Админка
     │ USB: прошивает bootstrap                        │                       │
     │ подключается к точке доступа устройства         │                       │
     │ вводит Wi-Fi в мини-странице ─►│                │                       │
     │                                │ POST /dev/v1/register/request          │
     │                                │  {mac, chip_rev, bootstrap_version,    │
     │                                │   dev_sign_pub, dev_kex_pub,           │
     │                                │   web_password (зашифрован под         │
     │                                │   K_telemetry),                        │
     │                                │   sig = ES256(dev_sign, всё выше)} ───►│
     │                                │◄──── {request_id, claim_code} ─────────│
     │ видит код на экране и странице │                │ прибор появляется  ──►│
     │                                │                │ в списке ожидающих    │
     │ выбирает прибор в списке, вводит код с экрана, выбирает профиль,        │
     │ задаёт параметры (superadmin: «прибор разработчика») ──────────────────►│
     │                                │                │◄── approve ───────────│
     │                                │                │ создаёт device, K_ota,│
     │                                │                │ конфиг v1             │
     │                                │ GET /dev/v1/register/status?request_id │
     │                                │  (опрос каждые 5 с, подписан dev_sign) │
     │                                │◄─ {device_id, serial,                  │
     │                                │    config: JWS(K_config),              │
     │                                │    ota_key: ECIES(dev_kex_pub, K_ota)} │
     │                                │ сохраняет в раздел identity            │
     │                                │ → обычный цикл обновления (7.3):       │
     │                                │   ставит app + www под свой профиль    │
```

Правила:
- **Код регистрации:** 8 символов Crockford Base32, действует 30 минут. После 5 неверных вводов в админке за 10 минут ввод блокируется для этого пользователя.
- **Список ожидающих.** Прибор, отправивший запрос, сразу виден на вкладке «Реєстрація»: MAC, ревизия чипа, версия bootstrap, IP, время. Код в списке не показывается. Инженер выбирает прибор и вводит код с его экрана. Код должен совпасть с кодом именно этого запроса: это подтверждает, что прибор у инженера в руках, а не просто где-то в сети. Можно и сразу ввести код, не выбирая прибор.
- **Повторный запрос с того же MAC** (перезапущенный bootstrap) отменяет предыдущий ожидающий. С одного IP принимается не больше 200 запросов в час (производственная линия часто выходит через один NAT).
- **Прибор разработчика** (флаг `dev` в подписанном конфиге) отмечает только `superadmin`: при регистрации или позже на странице прибора (7.3, «Сборки для разработки»).
- **MAC уже есть у зарегистрированного устройства:** запрос принимается, но при вводе кода админка показывает предупреждение и фиксирует аномалию `duplicate_registration`.
  - Для повторной регистрации того же устройства (например, после перепрошивки по USB) производитель явно выбирает действие «перерегистрировать существующее». При этом выдаются новые ключи, а старые аннулируются.
- **Отозванный производитель** не может подтвердить регистрацию.
- **Отозванное устройство** нельзя перерегистрировать. Сначала `superadmin` должен снять отзыв.

### 7.3 Проверка и установка обновлений

**Проверка.** Устройство вызывает `GET /dev/v1/update` после каждого подключения к сети и затем раз в 6 часов, пока есть связь (прибор разработчика — раз в 30 с; интервал приходит в ответе, `poll_after`). Если в ответе есть предложение и `mode=auto` (критический релиз), устройство ставит его сразу, но только при заряде АКБ не ниже 20 %. При меньшем заряде установка откладывается до зарядки. Если `mode=button`, устройство показывает пользователю кнопку «Обновить».

**Алгоритм выбора версии** (выполняется на сервере):

```
если device.status == revoked           → 403 {error: "device_revoked"}
если device.pending_release_id != null  → предложить его, mode=engineer
                                          (назначено инженером; любая версия,
                                          в том числе beta и откат)
если device.pinned                      → нет обновлений
R_crit = последний stable-релиз с critical=true, в котором есть профиль устройства
если R_crit найден и R_crit.version > current и не device.is_test
                                        → предложить R_crit, mode=auto
R_st = последний stable-релиз, в котором есть профиль устройства
если R_st.version > current             → предложить R_st, mode=button
иначе                                   → нет обновлений
```

- Версии сравниваются по правилам semver. Например, `1.3.0-beta.2` новее `1.2.5`, но старше `1.3.0`.
- Отсюда правило выпуска: **beta-версия должна содержать все исправления из предыдущих stable.** Тогда устройство, на которое инженер поставил beta, не нуждается в критическом исправлении для более старого stable, и откат не произойдёт.

**Манифест.** Это JWS, подписанный `K_manifest`. Он привязан к конкретному устройству и действует ограниченное время, поэтому его нельзя переиспользовать на другом устройстве или повторить позже.

```json
{
  "typ": "zir-manifest/1",
  "device_id": "…", "profile": "zir3m-full",
  "release_id": "…", "version": "1.4.0", "mode": "button",
  "critical": false,
  "app": { "needed": true,  "url": "/dev/v1/artifacts/<release>/app",
           "size": 1310720, "sha256": "<хеш расшифрованного app.bin>",
           "enc": "esp_encrypted_img" },
  "www": { "needed": true,  "url": "/dev/v1/artifacts/<release>/www",
           "format": "tar", "size": 143360, "sha256": "<хеш www.tar>",
           "version": "1.4.0", "www_api": 3 },
  "iat": 1762600000, "exp": 1762603600
}
```

- **Поле `needed`.** Сервер сравнивает `app_sha256` и `www_sha256`, которые устройство сообщает при аутентификации, с компонентами релиза. Если компонент не изменился, он не скачивается. Так работают релизы, где поменялась только веб-морда или только прошивка.
- **`GET .../app`** возвращает `app.bin`, зашифрованный ключом `K_ota` этого устройства в формате `esp_encrypted_img`. Зашифрованный образ кешируется в `/data/cache/<device>/<build>`.
- **`GET .../www`** возвращает архив `www.tar` (содержимое `dist/` веб-морды, текстовые файлы сжаты gzip). Он не шифруется (веб-морда не секретна). Устройство принимает только архив, хеш которого указан в подписанном манифесте или в подписанном контейнере `.zwww` (7.8). Распаковывает архив сама прошивка, поэтому образ LittleFS на сервере не собирается и параметры `mklittlefs` не нужно согласовывать с прошивкой.
- **Отчёт.** Устройство отправляет `POST /dev/v1/update/report {release_id, status, error?}`, сервер пишет его в `update_events`. После успешной установки сервер сбрасывает `pending_release_id`.

**Порядок установки на устройстве** описан в `FIRMWARE_REQUIREMENTS.md`, раздел 6. Коротко: прошивка → веб-морда → переключение слота загрузки → самопроверка → подтверждение. Если самопроверка не прошла, загрузчик откатывает прошивку.

### 7.4 Вход инженера

```
Инженер (браузер)           ESP32                          lcm
  │ «Инженерный вход» ──────►│                                 │
  │◄── 302 https://fw.<домен>/eng/login?device=<id>&nonce=<n>   │
  │        &return=http://<ip-устройства>/eng/callback          │
  │ логин + TOTP ─────────────────────────────────────────────►│
  │                          │  проверки: пользователь active,  │
  │                          │  есть роль engineer или          │
  │                          │  superadmin, устройство          │
  │                          │  существует                      │
  │◄── 302 <return>#token=<JWS(K_engtoken)> ────────────────────│
  │ страница устройства забирает токен из fragment ─►│          │
  │                          │ проверяет подпись, device_id,    │
  │                          │ nonce, exp                       │
  │                          │ если есть интернет:              │
  │                          │ POST /dev/v1/engineer/confirm    │
  │                          │   {jti} ────────────────────────►│ отмечает confirmed_at,
  │                          │◄──────── {ok, engineer_name} ────│ повторное использование
  │                          │                                  │ запрещено
  │◄── инженерная сессия ────│                                  │
```

**Содержимое токена:** `{typ:"zir-eng/1", jti, sub:<engineer_id>, name, dev:<device_id>, nonce, iat, exp: iat+300}`.

**`return` проверяется сервером.** Допускаются только адреса из частных сетей (RFC 1918) и адрес точки доступа устройства. Так сервер нельзя использовать для перенаправления на произвольный сайт.

**Почему токен в fragment (`#token=…`).** Fragment не отправляется на сервер и не попадает в логи прокси. Страница устройства передаёт его на устройство через POST.

**Вариант «б»** (у устройства нет интернета, у телефона инженера есть):
- шаг `confirm` пропускается, устройство проверяет токен только локально;
- токен одноразовый за счёт `nonce` (устройство помнит выданные `nonce`) и живёт 5 минут.

**Отзыв инженера:**
- новый токен ему не выдаётся;
- уже открытая инженерная сессия на устройстве живёт не дольше 30 минут;
- в варианте «а» устройство каждые 5 минут подтверждает сессию через `/dev/v1/engineer/confirm`, и при отзыве она закрывается сразу.

**Сборки для разработки.** Прошивка, собранная с `CONFIG_ZIR_DEV_BUILD=y` (локальная сборка в PlatformIO), разрешает включать инженерный режим переключателем в меню прибора, без сервера. Это нужно на этапе разработки. В боевых сборках переключателя нет, и инженерный режим открывается только по токену сервера.
- Флаг сборки записан во встроенное описание прошивки (`zir_custom_desc_t.flags`, FIRMWARE_REQUIREMENTS 6.4).
- Сервер **не подписывает** образ с этим флагом: сборщик проверяет его и завершает сборку с ошибкой.
- Устройство пользователя принимает по OTA и через ручную загрузку только подписанные образы. Поэтому сборка для разработки не может попасть на него ни через сервер, ни через веб-морду. Поставить её можно только по USB, а это на L0 и так никак не ограничено.
- **Исключение — прибор разработчика:** в его подписанном конфиге стоит `"dev": true`. Ставит флаг только `superadmin`, каждое изменение пишется в аудит и порождает новую версию конфига. Такому прибору сервер доставляет сборки для разработки по OTA:
  - сборка загружается в админке («Розробка»), командой `lcmctl push-dev` или целью PlatformIO; сервер проверяет, что бит dev установлен, и **не подписывает** её;
  - образ шифруется `K_ota` прибора, как любой другой: клон или чужой прибор его не расшифрует;
  - сборка назначается выбранным приборам разработчика (или всем приборам разработчика её профиля);
  - **критическая** сборка (`mode=auto`) ставится сразу, без кнопки и без проверки заряда; обычная показывает кнопку «Обновить»;
  - прибор разработчика опрашивает сервер раз в 30 с, поэтому критическая сборка встаёт в течение минуты;
  - пока сборка назначена, релизы прибору не предлагаются; назначение релиза инженером снимает её, и наоборот.
- Первый переход на сборку для разработки делает bootstrap: при `"dev": true` в конфиге, полученном при регистрации, он принимает образ без подписи. Боевая прошивка образ без подписи не установит даже на приборе разработчика.
- Это ослабление защиты, но небольшое: кто может поставить флаг `dev`, тот может залить на этот прибор любой код. На L0 то же самое и так можно сделать по USB.
- **Сборка для разработки привязана к серверу.** Без синхронизации с сервером она работает не больше часа наработки (`STAT_ON_S` плюс минута за каждое включение), затем обнаружение останавливается до следующей синхронизации. Синхронизация засчитывается, только если подписанный конфиг прибора содержит `"dev": true`. Отзыв прибора или снятие флага `dev` останавливают его сразу. Wi-Fi в такой сборке включён с момента старта. Так утёкшая сборка для разработки бесполезна на приборе, который сервер не признаёт прибором разработчика (FIRMWARE_REQUIREMENTS 10.1).

**Аудит.** Действия инженера на устройстве (смена параметров, установка версии, вход и выход) устройство пишет в локальный журнал и отправляет вместе с телеметрией. Сервер раскладывает их в `audit_log` с `actor_type='user'` и пометкой `via_device`.

### 7.5 Изменение жёстких параметров конфига

Изменить параметры можно двумя способами. Оба требуют связи с сервером.

1. **Из админки.** Инженер меняет параметры устройства, сервер подписывает конфиг версии `v+1`. Устройство получает его при следующей проверке обновлений: в ответе `GET /dev/v1/update` есть поле `config_version`. Если она больше текущей, устройство вызывает `GET /dev/v1/config`.
2. **Из инженерного меню устройства.**
   - **Вариант «а».** Устройство отправляет `POST /dev/v1/config/request {params, eng_jti}`, сервер проверяет токен инженера и возвращает подписанный конфиг.
   - **Вариант «б».** Устройство формирует запрос, подписанный `dev_sign`. Браузер инженера пересылает его на `POST /api/v1/devices/{id}/config/relay` в рамках сессии инженера в админке и возвращает подписанный конфиг на устройство.

**Проверки на сервере:**
- параметры соответствуют `hw_profiles.params_schema` (только модули профиля, диапазоны в разрешённых границах);
- инженер активен.

**Формат конфига** (JWS, подписанный `K_config`):

```json
{
  "typ": "zir-config/1",
  "device_id": "…", "mac": "28:05:a5:…", "profile": "zir3m-full",
  "version": 7, "iat": 1762600000,
  "modules": { "ft3500": true, "rx5808": true, "ta8804": true },
  "ranges":  { "ft3500": { "min": 2000, "max": 4050 },
               "rx5808": { "min": 4900, "max": 6184 },
               "ta8804": { "min": 900,  "max": 2250 } }
}
```

- **Жёсткие параметры** — только установленные модули и их частоты (`ranges`, МГц). Сканирование и ручная настройка не выходят за эти границы.
- **Мягкие параметры** на сервер не попадают. Они живут в NVS устройства без подписи:
  - пользовательские (включение диапазонов `band_*` среди установленных модулей, яркость, звук, Wi-Fi) — меняет пользователь;
  - инженерные (атенюаторы `atten_*`, калибровка и кривая разряда АКБ, пороги детектора) — меняются только в инженерной сессии на устройстве.

### 7.6 Телеметрия

Устройство отправляет `POST /dev/v1/telemetry` при каждом подключении к серверу. Если накопилось несколько пакетов, они отправляются пачкой. Как копить телеметрию офлайн, решает прошивка.

**Конверт пакета** — двойная защита поверх TLS:

```
header  = {typ:"zir-tlm/1", device_id, seq, eph_pub, iv}
plain   = JSON {seq, device_time, uptime_s, app_version, release_id,
                stats: {...}, events: [...], engineer_audit: [...], ...}
key     = HKDF-SHA256(ECDH(eph_priv, K_telemetry_pub), info="zir-tlm/1")
ct      = AES-256-GCM(key, iv, plain, aad=header)
packet  = header || ct || ES256(dev_sign, header || ct)
```

**Порядок проверки на сервере:**
1. Подпись проверяется ключом `dev_sign_pub`. Если неверна — отказ и аномалия `bad_signature`.
2. Пакет расшифровывается.
3. Если `seq` не больше `last_seq`, пакет отклоняется как повтор, фиксируется аномалия `seq_replay`.
4. Если `stats.on_s` (наработка) меньше `max_on_s`, пакет принимается, но фиксируются аномалия `counter_decrease` и уведомление `superadmin`.

**Сброс `seq`.** Если устройство перепрошили по USB и `seq` начался заново, это тоже `seq_replay`. После проверки инженер может сбросить счётчик в админке; действие попадает в аудит.

**Состав телеметрии** — всё, что прибор считает:
- весь блок `stats` (то же, что `GET /api/info` прибора): наработка `on_s`, `screen_s`, `wifi_s`, число запусков и причины перезагрузок (`rst_*`), ошибки I2C и АЦП, старт экрана, глубокие разряды АКБ, результаты самопроверки (`selftest_*`);
- `reset_reason` последнего старта, `heap_min`;
- сводка последнего сбоя, если есть (задача, причина, backtrace, `app_sha256`);
- события: обнаружения сигналов (канал, частота), `battery_low`, смена режимов. У каждого события есть `boot` и `uptime_s`. Время `time` есть, только если прибор знал время (Wi-Fi и SNTP в том же запуске), иначе `null`. Сервер принимает события без времени и упорядочивает их по `boot` и `uptime_s`;
- журнал действий инженера `engineer_audit`.

Поле `payload` в БД имеет тип `jsonb`, поэтому новые поля добавляются без миграций. Наработка дополнительно выносится в `device_counters`.

### 7.7 Core dump

После перезагрузки из-за сбоя устройство отправляет `POST /dev/v1/coredump`. Тело — такой же конверт, как у телеметрии (тип `zir-core/1`), с содержимым раздела `coredump` (до 64 КБ).

- Сервер сохраняет файл в `/data/coredumps` зашифрованным мастер-ключом и связывает его с `app_sha256` и сборкой.
- В админке инженер скачивает core dump вместе с ELF нужной сборки и разбирает их командой `idf.py coredump-info`. Поэтому **ELF каждой сборки хранится всегда**.
- После подтверждения приёма устройство очищает раздел `coredump`.

### 7.8 Ручная загрузка `www` через страницу восстановления

Для каждого `www`-билда сервер формирует контейнер `www-<version>.zwww`, который можно скачать в админке:

```
magic "ZWWW" | u16 header_len | header JSON {version, www_api, size, sha256}
            | u16 sig_len | ES256(K_www, header) | www.tar
```

- Подпись покрывает заголовок, а заголовок содержит SHA-256 архива. Поэтому устройство проверяет подпись **до** приёма архива, а хеш — по мере потоковой распаковки.
- Боевая прошивка принимает вручную только такой контейнер (через веб-морду и страницу восстановления). Сырой `www.tar` принимает только сборка для разработки (`CONFIG_ZIR_DEV_BUILD`).
- Ручная загрузка `app.bin` остаётся в любой сборке. Прошивка всё равно проверяет подпись RSA-3072, поэтому поставить можно только образ, подписанный сервером.

### 7.9 Отзыв

| Объект | Что происходит |
|---|---|
| **Устройство** | `status=revoked`. Эндпоинты `/dev/v1/update`, `/artifacts`, `/config`, `/engineer/confirm` возвращают `403 device_revoked`. Устройство показывает пользователю «обновления недоступны». Телеметрия и core dump принимаются и помечаются. Повторная регистрация того же MAC запрещена. Инженерные токены для устройства не выдаются. |
| **Инженер** | `status=revoked`. Сессии в админке завершаются, токены не выдаются, `confirm` для его `jti` возвращает отказ. Открытые сессии на устройствах закрываются в течение 5 минут (вариант «а») или не дольше чем через 30 минут (вариант «б»). |
| **Производитель** | То же, что для инженера, и плюс не может подтверждать регистрацию. Зарегистрированные им устройства остаются активными. |
| **Восстановление** | Только `superadmin`, с обязательным указанием причины. Действие пишется в аудит. |

### 7.10 Смена пароля точки доступа

Пользователь может сменить пароль точки доступа в веб-морде. Новый пароль нужен инженеру для подключения при обслуживании, поэтому устройство сообщает его серверу.

- Устройство отправляет `POST /dev/v1/web-password` при ближайшей связи с сервером после смены. Тело — конверт как у телеметрии (тип `zir-pwd/1`, 7.6) с полями `{seq, password, changed_at}`. Номер `seq` общий с телеметрией.
- Сервер сохраняет пароль в `devices.web_password_enc` и пишет событие в аудит (без самого пароля).
- Пока сервер не подтвердил приём, устройство хранит флаг «пароль не отправлен» и повторяет отправку.
- Пароль виден в админке инженеру и `superadmin` (`GET /api/v1/devices/{id}/web-password`), просмотр пишется в аудит.

## 9. Сборка прошивок и релизы

### 9.1 Репозитории (GitHub, приватные)

- **firmware-репо** (`ZIR_3M`). Одна кодовая база. Модули включаются флагами Kconfig (`CONFIG_ZIR_MODULE_FT3500`, `CONFIG_ZIR_MODULE_TA8804`; RX5808 есть всегда), в коде — через `#ifdef`.
  - Профили лежат в `profiles/<code>/sdkconfig.defaults`, например `zir3m-full`, `zir3m-no-3g3`.
  - Bootstrap — отдельный проект в `bootstrap/` того же репо.
  - Разработчики собирают прошивку в PlatformIO, сервер — через `idf.py`. Проект должен собираться обоими способами (FIRMWARE_REQUIREMENTS, раздел 1).
- **www-репо** (`zir-web-ui`). Одна веб-морда на все профили. Состав экранов определяется по данным устройства: модули из `state` (`fitted`) и `GET /api/info`. Договорённости для репозитория:
  - `npm ci && npm run build && npm run pack` даёт `www.tar`;
  - в архиве лежит **несжатый** `manifest.json` с `{version, www_api}` (прошивка читает его при старте, поэтому скрипт сжатия его пропускает).
- У сервера к каждому репо есть **deploy key только для чтения**.

### 9.2 Сборщик

Сборщик — Go-воркер в образе на базе `espressif/idf:v6.0.x` (та же версия, что у прошивки) с Node.js. Задания он берёт из PostgreSQL (`SELECT … FOR UPDATE SKIP LOCKED`).

**Сборка `app` для профиля:**
1. `git clone` по `commit_sha` (ref фиксируется в коммит при постановке задания).
2. Номер версии берётся из тега (`v1.4.0`) или из `git describe` для beta.
3. Сборка:

   ```
   idf.py -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.release.defaults;profiles/<code>/sdkconfig.defaults" \
          -D ZIR_PROFILE=<code> -D ZIR_VERSION=<version> build
   ```

   `sdkconfig.release.defaults` — боевая конфигурация прошивки (логи вырезаны при компиляции). Сервер всегда собирает боевую конфигурацию, в том числе для `beta`.

4. Результат: `app.bin` (без подписи), `app.elf`, лог сборки.
5. Сборщик читает встроенное описание (`zir_custom_desc_t`) и проверяет:
   - профиль совпадает с ожидаемым;
   - флаг `ZIR_DESC_FLAG_DEV_BUILD` **не** установлен. Иначе сборка завершается с ошибкой и не подписывается.
6. Считается `comparable_hash`: хеш образа, в котором поля версии, даты и `ZIR_VERSION` в описании приложения заменены нулями.

**Сборка `www`:** `npm ci && npm run build && npm run pack` → `www.tar`. Сборщик проверяет, что в архиве есть несжатый `manifest.json` и что распакованное содержимое помещается в раздел `www` (`0xd8000`, с запасом на служебные блоки LittleFS). Затем сервер формирует контейнер `.zwww` (7.8).

**Сборка `bootstrap`:** `bootloader.bin`, `partition-table.bin`, `bootstrap.bin`. После подписи формируется zip-пакет для производителя со скриптом `flash.sh`/`flash.bat` на `esptool`.
*Реализовано иначе (PLAN.md):* сервер хранит один образ с 0x0 (`zir3m-bootstrap-<версия>.bin`) без подписи и прошивает его из браузера (раздел 10).

**После сборки** артефакты передаются в `lcm`. Модуль `signer` подписывает `app.bin` и `bootstrap.bin` ключом RSA-3072 (формат блока подписи Secure Boot V2). Реализация на Go покрывается тестом совместимости с `espsecure.py verify_signature --version 2`.

**Ограничения контейнера сборщика:** `mem_limit: 4g`, `cpus: 2`. Одновременно выполняется одна сборка. Сеть открыта только до GitHub, реестра npm и реестра компонентов ESP-IDF (`components.espressif.com`, оттуда приходят `littlefs`, `cjson`, `esp_encrypted_img`). Версии компонентов зафиксированы в `dependencies.lock` репозитория прошивки.

### 9.3 Жизненный цикл релиза

```
superadmin: «Собрать» (ветка/тег, профили) ──► builds (app × профили, www)
        │       (или webhook на push в выбранную ветку → автоматическая beta-сборка)
        ▼
superadmin: «Создать релиз» → releases(channel=beta), отмечаются профили
        │   подсказка: «для профиля X comparable_hash не изменился — можно не включать»
        ▼
инженеры ставят beta на устройства вручную, тестируют
        ▼
superadmin: «Перевести в stable» (тот же бинарник, без пересборки)
        │   опционально: «Критический»
        ▼
устройства: при проверке видят кнопку «Обновить» (или ставят сами, если релиз критический)
```

Релиз не меняется после перевода в `stable`. Чтобы исправить ошибку, выпускается новый релиз.

## 10. Bootstrap и Provisioning

- **Пакет bootstrap не содержит секретов.** В нём только подписанный bootstrap и публичные ключи сервера. Поэтому его можно спокойно раздавать производителям.
- **Утечка пакета ничего не даёт злоумышленнику:** без подтверждения производителем в админке устройство не получит ни ID, ни ключи, ни рабочую прошивку.
- **Отдельная утилита на Go на первом этапе не нужна:** достаточно `esptool` из скрипта в пакете. Позже можно сделать Go CLI, который сам скачивает актуальный пакет и показывает код регистрации из последовательного порта.
- **Прошивка из админки (реализовано).** Вкладка «Прошивка USB» (роли manufacturer и engineer) пишет bootstrap
  через USB-UART адаптер (CH340, CP210x, FTDI) прямо из браузера: Web Serial и esptool-js, встроенный в
  бинарник сервера. Нужны Chrome, Edge или Opera на компьютере и HTTPS. Страница пишет только flash. eFuse не
  трогаются (L0). Перед записью проверяется чип: ESP32, ревизия ≥ 3. После записи — сверка MD5 и запись
  `bootstrap.flash` в аудит (MAC, версия, кто). Образ сервер принимает, только если в нём ключ конфигов этого сервера:
  bootstrap, собранный для другого сервера, не прошьётся по ошибке.

## 11. Развёртывание на VPS

**`docker-compose.yml`** (сеть Traefik — внешняя, уже существующая):

```yaml
services:
  lcm:
    image: zir/lcm:<ver>
    environment:
      DATABASE_URL: postgres://lcm@postgres/lcm
      MASTER_KEY_FILE: /run/secrets/master_key
      PUBLIC_URL: https://fw.<домен>
    secrets: [master_key]
    volumes: [ "/srv/fw/data:/data" ]
    labels:
      - traefik.enable=true
      - traefik.http.routers.fw.rule=Host(`fw.<домен>`)
      - traefik.http.routers.fw.tls.certresolver=letsencrypt
      - traefik.http.services.fw.loadbalancer.server.port=8080
    networks: [traefik, internal]
  builder:
    image: zir/builder:<ver>          # FROM espressif/idf:v6.0.x (версия прошивки)
    environment: { DATABASE_URL: postgres://builder@postgres/fw }
    volumes: [ "/srv/fw/data/builds:/builds" ]
    mem_limit: 4g
    cpus: 2
    networks: [internal, egress]
  postgres:
    image: postgres:16
    volumes: [ "/srv/fw/pg:/var/lib/postgresql/data" ]
    networks: [internal]
secrets:
  master_key: { file: /srv/fw/secrets/master.key }   # chmod 600
```

- **У сборщика своя роль БД** с правами только на таблицу заданий. Доступа к ключам и к таблицам устройств у неё нет.
- **Лимиты запросов** настраиваются в Traefik (middleware `ratelimit`) на `/eng/login`, `/api/v1/auth/*`, `/dev/v1/register/*`. Дополнительно `lcm` ограничивает попытки входа: 5 неудач — пауза 15 минут.
- **Бэкапы:**
  - `pg_dump` каждую ночь и `rsync` каталога `/data/artifacts` во внешнее хранилище, например S3-совместимое у другого провайдера;
  - мастер-ключ и ключ подписи прошивок хранятся **офлайн**, отдельно от бэкапов;
  - восстановление проверяется раз в квартал.
- **Мониторинг:**
  - `GET /healthz`;
  - логи в формате JSON в stdout, без секретов;
  - уведомления `superadmin` на e-mail о новых аномалиях и упавших сборках.

## 13. Переход на L1 и L2

**L1 (Flash Encryption):**
1. Сервер генерирует `K_flash` для устройства и сохраняет его в `devices.flash_key_enc`.
2. Ключ прожигается по USB специальной процедурой производителя (`espefuse.py burn_key flash_encryption`) или передаётся устройству для самостоятельного прожига (решается на этапе L1).
3. Включается шифрование NVS: раздел `nvs_keys` уже зарезервирован.
4. На сервере меняется только `security_level` и появляется процедура выдачи ключа. Протоколы остаются прежними.

**L2 (Secure Boot V2):**
- используется тот же ключ RSA-3072, которым уже подписываются прошивки: его хеш прожигается в eFuse;
- ключ не меняется, поэтому весь парк устройств, обновлённых по OTA, совместим без изменений.

## 14. План реализации

1. **Фундамент:** каркас Go-проекта, БД и миграции, пользователи (argon2id, TOTP, роли), аудит, `lcmctl init-keys`, развёртывание за Traefik.
2. **Устройства:** профили, регистрация по коду, аутентификация устройств, подписанные конфиги, симулятор устройства.
3. **Сборка и релизы:** сборщик (app, www, bootstrap), подпись, релизы, каналы, webhook.
4. **OTA:** алгоритм выбора версии, манифесты, `esp_encrypted_img`, отчёты, закрепление версии, тестовые устройства, критические релизы.
5. **Инженерный доступ:** вход, токены, `confirm`, изменение конфига (оба варианта).
6. **Телеметрия и диагностика:** конверты, аномалии, core dump, уведомления.
7. **Отзыв и админка:** полный набор экранов, отзыв и восстановление, отчёты для роли `admin`.
8. **Совместная отладка с прошивкой** на реальных устройствах, проверка варианта «б» на телефонах инженеров.

## 15. Открытые вопросы на будущее

- Ограничение доступа инженеров группами устройств (по клиенту или региону). В модель данных добавляются `device_groups` и `user_device_groups`.
- Мультитенантность (несколько клиентов-владельцев) пока не нужна.
- Решение бизнеса о переходе на L1.
